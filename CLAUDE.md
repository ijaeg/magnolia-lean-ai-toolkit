# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Magnolia CMS (community edition, 6.4.9) module scaffolded from the standard Magnolia archetype, adding a "Fact Checker" feature for content editors. An editor selects a page (or component) in the Magnolia admin app and triggers a "Fact Check" action, which extracts factual claims from configured content properties using an LLM, verifies each claim against Wikipedia, and posts the results back to the editor as an in-app message.

## Build

Maven multi-module, Java 21.

```
mvn clean install                                          # build everything
mvn -pl magnolia-lean-ai-factchecker-module clean install   # build just the module
mvn -pl magnolia-lean-ai-factchecker-module test            # run the module's unit tests
mvn -pl magnolia-lean-ai-factchecker-module test -Dtest=FactCheckerServiceImplTest   # run a single test class (JUnit 4)
```

Unit tests (JUnit 4 + Mockito) live under `magnolia-lean-ai-factchecker-module/src/test/java`, covering `FactCheckerServiceImpl`, `FactCheckCommandAction`, `WikipediaTool`, `PageSubnodesPredicate`, and `ChatModelFactory`.

## Running

There is no `jetty:run`/`cargo` Maven plugin configured. The webapp is built as a WAR (`magnolia-lean-ai-toolkit-webapp`) and run locally via an application server (this repo's IntelliJ run config points at a local Tomcat deployment). By default the module is configured against Ollama running locally (`http://localhost:11434`) with the models referenced in `config.yaml` pulled, or the fact-check action will fail when it calls out to the chat models.

## Module layout

- `magnolia-lean-ai-toolkit-webapp` — a thin Magnolia `magnolia-community-webapp` bundle (WAR) with vendor overlay files under `overlays/`; it exists to host the module, has no custom code, and can generally be ignored.
- `magnolia-lean-ai-factchecker-module` — all the actual code and Magnolia configuration.

## Architecture (factchecker module)

**Trigger → command → service pipeline.** The action is wired into both the Pages app's browser/detail subapps and (for demo purposes) the Tours app via `decorations/*/apps/*.yaml`, and flows through these layers:

1. **UI action** (`decorations/pages-app/apps/pages-app.yaml`, `decorations/tours/apps/tours.yaml`) registers a `factCheck` action of `$type: factCheckCommandAction` on the item actionbar (browser, detail/page, and component action groups), bound to Magnolia command `factChecker`. The Pages app wiring passes `params: { includeSubnodes: true, checkAllLanguages: true }`.
2. `FactCheckCommandActionDefinition` / `FactCheckCommandAction` (`action/`) — a `JcrCommandAction` subclass. After the underlying command runs, it reads results the command stashed in `MgnlContext` under the key `FactCheckerCommand.FACTCHECK_RESULTS_ATTR`, formats them as HTML (message subject/pattern/description templates all live on the definition, overridable in config), and sends a local `Message` (view `magnolia-lean-ai-factchecker-module:factCheck`, defined by `messageViews/factCheck.yaml`) so results show up in the editor's notification/message center. Message type is `WARNING` if any claim came back `INCORRECT`, else `INFO`. `result.explanation()` (LLM-generated, so untrusted) is HTML-escaped via `StringEscapeUtils.escapeHtml4` before being interpolated into the message HTML — note `claim`/`verdict`/`sourceUrl` currently are not, so keep that in mind if extending this formatting.
3. `FactCheckerCommand` (`command/`, registered in `mgnl-bootstrap/.../commands.yaml` as command `factChecker` with `nodePropertyNames: [body, text]`) — a `BaseRepositoryCommand`. For the target node, it iterates the configured `nodePropertyNames`; for each property it resolves the value via the site's (or fallback) `I18nContentSupport`, checking either just the default locale or every locale (`checkAllLanguages`), and optionally recurses into content subnodes belonging to the same page (`includeSubnodes`, using `PageSubnodesPredicate`). Each non-empty property value + its locale is passed to `FactCheckerService.check(text, language)`. All results are aggregated and written back into `MgnlContext` (`Context.LOCAL_SCOPE`) for the action (step 2) to pick up. **This context-passing convention (command writes to `MgnlContext`, action reads it after `super.executeCommand`) is how results cross the command/action boundary — preserve it if you touch either class.**
4. `FactCheckerServiceImpl` (`service/`) — the core logic, using LangChain4j `AiServices`. The two AI-service interfaces it builds proxies for (`ClaimExtractor`, `FactChecker`) live in `agent/`, not `service/`:
   - **Claim extraction**: a chat model (`ClaimExtractor` AI service) turns free text into a list of claim strings, given the text and its language. The system prompt (externalized to a resource file, see below) is deliberately strict about excluding opinions/marketing language/inferred totals and about cross-sentence reference resolution — see the prompt's own "Examples" section before changing it.
   - **Fact checking**: a second chat model (`FactChecker` AI service) checks each claim one at a time, given the claim and its language, calling the `wikipediaLookup` tool to verify it, and returns a `FactCheckResult` (`Verdict.CORRECT/INCORRECT/UNVERIFIABLE`, explanation in the claim's language, source URL). The service wraps each into a `ClaimCheckResult` (claim + verdict + explanation + sourceUrl) for the command/action layer.
   - Two independently configured `ChatModelConfig`s are used (claim extraction vs. fact checking), built per-call by `ChatModelFactory` — see `FactCheckerModule` for the config bean shape and `config.yaml` for the deployed defaults (currently `qwen2.5:7b-instruct` for extraction, `llama3.1:8b-instruct-q4_K_M` for checking, both via Ollama).
5. `ChatModelFactory` (`factory/`) — builds a LangChain4j `ChatModel` from a `ChatModelConfig` based on its `providerType` (`OLLAMA`, `OPEN_AI`, or `ANTHROPIC`; the corresponding `langchain4j-ollama`/`langchain4j-open-ai`/`langchain4j-anthropic` deps are all on the classpath). Only Ollama is exercised by the checked-in `config.yaml`; `includes/openaiChatModelConfig.yaml` exists as an alternate template but isn't currently `!include`d anywhere. For `OPEN_AI`/`ANTHROPIC`, `apiKey` in config is not the literal secret — it's a JCR node path into Magnolia's Passwords App keystore (`PasswordManagerCoreModule.KEYSTORE_WORKSPACE`); the factory resolves it via `SessionUtil.getNode` + the injected `PasswordRegistry` (`getApiKeyFromKeyStore`), returning `null` if the node can't be found (logged, not thrown).
6. `WikipediaTool` (`tool/`) — a LangChain4j `@Tool`, invoked by the fact-checker AI service with `(query, context, language)`, that searches Wikipedia in the requested language (via a Magnolia `RestClient` resolved dynamically by `{language}.wikipedia`, e.g. `en.wikipedia`/`de.wikipedia` — see `restClients/*.wikipedia.yaml` — falling back to `en.wikipedia` if no client is registered for that language) and fetches an article summary. It has non-trivial disambiguation logic (`isClearlyBestMatch`) to avoid confidently returning the wrong article for ambiguous entity names, and returns a typed `NOT_FOUND`/`AMBIGUOUS`/`FOUND` result rather than guessing — the fact-checker prompt relies on this to fall back to `UNVERIFIABLE` correctly.

## Configuration

- `FactCheckerModule` (module class, `@Data` via Lombok) defines the config bean tree bound from `config:/modules/magnolia-lean-ai-factchecker-module`: two `ChatModelConfig`s (`claimExtractorChatModelConfg`/`factCheckerChatModelConfg` — providerType, baseUrl, apiKey, modelName, numCtx, numPredict, temperature, `timeoutInSeconds`, request/response logging, `supportedCapabilities`). `apiKey` here is a Passwords App node path, not a plaintext secret (see `ChatModelFactory` above). `timeoutInSeconds` is a primitive `long` with no default (0 if unset) — `ChatModelFactory` passes it straight into `Duration.ofSeconds(...)`, and a zero/unset value makes the underlying HTTP client throw `IllegalArgumentException: Invalid duration: PT0S` at chat-model build time; both `includes/ollamaChatModelConfig.yaml` and `includes/openaiChatModelConfig.yaml` set it (150s) for this reason, and anything constructing a `ChatModelConfig` directly (e.g. tests) must set it too. Note `createAnthropicChatModel` in `ChatModelFactory` does not currently apply this timeout at all. Full property reference (including defaults not repeated here): `magnolia-lean-ai-factchecker-module/config.md`.
- `src/main/resources/magnolia-lean-ai-factchecker-module/config.yaml` sets the deployed chat-model defaults, `!include`-ing the shared template `includes/ollamaChatModelConfig.yaml` and overriding per-model fields (model name, `numCtx`, temperature; the extractor also sets `supportedCapabilities: RESPONSE_FORMAT_JSON_SCHEMA`, the checker does not — see pitfall below). Change model names/temperatures/context size here, not in Java.
- The two system/user prompts are **not** in `config.yaml` — they're plain-text resource files under `src/main/resources/prompts/` (`claimExtractorSystemMessage.txt`, `claimExtractorUserMessage.txt`, `factCheckerSystemMessage.txt`, `factCheckerUserMessage.txt`), loaded by `ClaimExtractor`/`FactChecker` via `@SystemMessage(fromResource = ...)`/`@UserMessage(fromResource = ...)`. Edit these files directly to change prompt wording; a redeploy is needed to pick up changes (they're not hot-reloaded from JCR like the rest of this section).
- `restClients/en.wikipedia.yaml` and `restClients/de.wikipedia.yaml` define the per-language Wikipedia REST endpoints (`search`, `summary`) consumed by `WikipediaTool`, both `!include`-ing the shared `includes/userAgentHeader.yaml` for request headers; add a new `restClients/{lang}.wikipedia.yaml` to support another language.
- All of the above is standard Magnolia YAML-based light module configuration, bootstrapped/merged into the JCR config workspace at startup — editing these files and restarting (or redeploying) picks up changes.

## Regression tests for prompt logic (`*RegressionIT`)

Unit tests cover infrastructure (Wikipedia tool, JSON parsing, retry/null-handling) but not prompt-logic quality, which needs a live model. `ClaimExtractorRegressionIT` and `FactCheckerRegressionIT` (package `info.ijaeg.mgnl.ai.regression`) close that gap by exercising the real prompts against a live local Ollama instance.

- Naming convention `*RegressionIT.java` puts them under `maven-failsafe-plugin` (configured in this module's `pom.xml`, not the root POM — only this module has tests), so they run only on `mvn verify`/`mvn install`, never on the fast `mvn test`/Surefire pass; they need Ollama running locally with both configured models pulled and are not fully deterministic.
- Only `WikipediaTool` is faked (`FakeWikipediaTool`, same `@Tool`/`@P` signature and description text as the real tool, fuzzy substring lookup against fixture data via `fixtures.entrySet().stream().filter(e -> query.contains(e.getKey())).findFirst()`) — the `ChatModel` itself is real, built via the same `ChatModelFactory.createChatModel(...)` call production uses, so a change to that factory shows up here too, not just in `ChatModelFactoryTest`.
- Test data (text, expected substrings, Wikipedia fixtures, expected verdict) lives as one JSON file per case under `src/test/resources/regression-testdata/{extractor-cases,checker-cases}/`, loaded via `RegressionCaseLoader.loadExtractorCases(...)`/`loadCheckerCases(...)` by scanning a classpath directory. This only works against exploded `target/test-classes` (the Surefire/Failsafe default), not from inside a packaged jar. Jackson deserializes each file into an `ExtractorCase`/`CheckerCase` record by component name via `Class.getRecordComponents()` (databind ≥2.12) — this does not need the `-parameters` compiler flag, which only affects ordinary constructor/method parameters, not record components.
- Test content is a self-contained fictional world (Velmora/Kordinia and others), not the original Magnolia Travel Demo content or real politicians' names used during earlier manual debugging — same structural bug patterns, no dependency on demo content or real people.
- Each test method collects and reports every failing case in one run instead of failing fast, so a run gives a full picture of broken vs. intact prompt behavior in one pass.

## Security note

`apiKey` values in config YAML (e.g. `includes/openaiChatModelConfig.yaml`) are node paths into the Magnolia Passwords App keystore, resolved at runtime by `ChatModelFactory`/`PasswordRegistry` — not plaintext secrets. Keep it that way: don't paste a literal API key into config YAML. Earlier git history (before the "store api keys in Passwords App" change) does contain a plaintext key in this file, so treat that history as compromised if this repo is ever made public.

## Design decisions & known pitfalls (from extensive local testing with quantized models)

These were discovered through iterative testing against real (English-language, travel-domain) content on `llama3.1:8b-instruct-q4_K_M` / `qwen2.5:7b-instruct`. They explain *why* the code looks the way it does — read before "simplifying" any of this.

### Separate `ChatModel` configs per AI service, on purpose
`ClaimExtractor` and `FactChecker` deliberately use two independently built `ChatModel` instances (not a shared one), because the two tasks have conflicting requirements:
- Extraction needs strict instruction-following and near-determinism (`qwen2.5:7b-instruct`, low temperature).
- Fact-checking needs reliable tool-calling (`llama3.1:8b-instruct`, which supports it better).

### Testing code that builds `AiServices` proxies (e.g. `FactCheckerServiceImpl`)
`AiServices.builder(...).chatModel(...).build()` returns a real dynamic proxy that does real JSON extraction/parsing against whatever `ChatModel` it's given — a plain Mockito `mock(ChatModel.class)` doesn't help here since every method (including the interface's default ones) comes back null/no-op. To unit-test this path (see `FactCheckerServiceImplTest`), write a small hand-rolled class `implements ChatModel` and override only `doChat(ChatRequest)` — the interface's default `chat(ChatRequest)` (which AiServices actually calls) does its own parameter-merging/listener-notification and then delegates to `doChat`, so overriding just that one method is enough to return a canned `ChatResponse`/`AiMessage` and exercise real parsing (including real `OutputParsingException`s from malformed text). Also note `FactCheckerServiceImpl.getModule()` calls `moduleRegistry.getModuleInstance(FactCheckerModule.class)` fresh each time, and its two `ChatModelConfig` fields are Lombok `@Data` (structurally equal when both are untouched defaults) — so when stubbing `chatModelFactory.createChatModel(...)` to return different fakes for the extractor vs. the checker, match by reference identity (`config == module.getClaimExtractorChatModelConfg()`) inside a Mockito `thenAnswer`, not by `equals()`, or the two stubs collide.

### `RESPONSE_FORMAT_JSON_SCHEMA` is enabled only for `ClaimExtractor`, not `FactChecker`
This is intentional, not an oversight (set via `supportedCapabilities` in `config.yaml`, not in Java). Combining Ollama's grammar-constrained JSON-schema output with tool-calling in the *same* request caused the model to skip the `wikipediaLookup` tool call entirely and fabricate an answer straight away (observed via `logRequests`/`logResponses`: `done_reason: "stop"` after a handful of tokens, no `tool_calls` in the response). Enabling the capability only where no tool is involved (extraction) avoids this; the fact-checker instead relies on prompt instructions for its JSON shape (see the strict field-order/no-extra-text instructions in `FactChecker`'s `@UserMessage`), which is less strict but keeps tool-calling reliable.

**If you revisit this**: the clean fix (not yet implemented) is splitting `FactChecker` into two phases — a tool-enabled "research" call without schema constraint, followed by a schema-constrained "judge" call with no tools — so each call only has to do one of the two things well.

### Ollama's auto-derived JSON schema does not mark fields `required`
LangChain4j's automatic schema generation from a Java record currently produces `"required": []` for every property, even for non-optional record components. Consequence: models can (and, under `qwen2.5:7b-instruct`, sometimes do) return `{}` for an empty result instead of `{"claims": []}`, which deserializes to `null`, not an empty list. **Always defensively null-check `AiServices` results before iterating** (see `extractClaims()` in `FactCheckerServiceImpl`) rather than assuming the record's non-null contract holds. The system prompt also explicitly spells out `{"claims": []}` as the expected empty-result shape, as a second line of defense (not a guarantee on its own).

### `FactCheckResult.explanation` can occasionally be empty
At `temperature > 0`, the fact-checker model sometimes returns syntactically valid JSON with an empty `explanation` string — most often in `UNVERIFIABLE` cases where no tool result gives it anything to paraphrase. This is sampling variance, not a deserialization bug (confirmed via raw response logs). Lower temperature reduces but doesn't eliminate it; a retry-once-on-empty-explanation is a reasonable mitigation if this becomes a visible problem in the UI.

### `WikipediaTool` search strategy: bare query first, context only on ambiguity
Do not concatenate `query + " " + context` as the default search string. Early versions did this and it broke searches for claims that relate two proper nouns (e.g. entity "Ho Chi Minh City" with context "Saigon river") — the combined phrase returned unrelated disambiguation stubs instead of the correct article. Current strategy: search the bare entity name first; only fall back to a context-refined search if the bare search is empty or genuinely ambiguous (`isClearlyBestMatch`).

Also watch the URL encoding in `search()`: `URLEncoder.encode(...)` produces `+` for spaces (form-encoding convention), which the MediaWiki REST search endpoint does not reliably interpret as a space — the code post-processes `+` to `%20` for this reason. Don't drop that replacement.

`search()`/`findWikpediaSummary()` call `verifyResponse()` before reading the body, which throws if `response.getStatus() != 200` or the media type isn't JSON-compatible; that throw is caught by the same method's own try/catch and silently degrades to an empty hit list / `NOT_FOUND`. When mocking `jakarta.ws.rs.core.Response` in tests (`WikipediaToolTest`), stub `getStatus()` (→ `HttpStatus.SC_OK`) and `getMediaType()` (→ `MediaType.APPLICATION_JSON_TYPE`) in addition to `getEntity()` — otherwise every test silently gets `NOT_FOUND`/empty results instead of a real assertion failure pointing at the cause.

### `isClearlyBestMatch` disambiguation heuristic
Checks two signals, in order: (1) an exact title match against `query` with no competing exact match among the other candidates — strong enough to trust without context; (2) if no exact match, whether the top candidate's description contains the first word of `context` and the runner-up's doesn't. With an empty `context` and more than one hit, this method returns `false` (i.e. `AMBIGUOUS`) unless there's an exact title match — don't "fix" this by loosening it without a matching test case, it was deliberately made conservative (a false `UNVERIFIABLE` is preferable to a confidently wrong verdict).

### `ClaimExtractor.ClaimList` currently returns raw strings, not `Claim{statement, originalSnippet}`
This is a known regression/gap, not the intended final design: the original plan was for each extracted claim to carry the exact source-text snippet it came from, so the editor-facing message can point at the specific sentence in the content, not just repeat the claim in isolation. `List<String>` currently loses that traceability. If working on the editor-facing message formatting, this is the first thing to restore.

### `numCtx` matters more than it looks
Ollama silently truncates input beyond the configured `numCtx` (no error) — with the fairly long `ClaimExtractor` system prompt (multiple few-shot examples), truncation risk is real for longer content bodies. Current default is `8192` for the extractor, `4096` for the checker. If claim extraction starts silently missing content from the *end* of long pages, check this before assuming it's a prompt-quality issue. (For the related `numPredict` pitfall with reasoning models, see below.)

### Extractor prompt: the few-shot examples are load-bearing, not decorative
The system prompt's rules alone were repeatedly insufficient on their own with the quantized 7B/8B models under test — each rule needed a matching few-shot example before the model reliably followed it:
- Reputation/superlative statements ("has earned a place among...", "one of the world's most...", "finest food you've ever eaten") are excluded, but the model doesn't generalize this across surface forms — different phrasings of the same "unfalsifiable acclaim" pattern have needed separate examples.
- Cross-sentence coreference resolution (e.g. "Ho Chi Minh City... The capital is...") needed its own example after being missed entirely with only a same-sentence example present — this is how the model previously silently dropped a genuinely incorrect claim (Ho Chi Minh City is not Vietnam's capital) instead of flagging it.
- The "split compound sentences into separate claims" rule likewise needed a worked example (the Mekong-delta tour text) — without it, multi-fact sentences were extracted as one bundled, imprecisely-checkable claim.

If claim quality regresses after a prompt edit, suspect the few-shot examples were trimmed or reordered past the model's effective context window before suspecting the rules themselves. These prompts live in `src/main/resources/prompts/*.txt`, not in Java source or `config.yaml` — check there first.

### Regression-test classes must stay on JUnit 4
The module's `pom.xml` only declares `junit:junit` (JUnit 4). Adding `junit-jupiter-api` without a matching `junit-jupiter-engine`/`junit-platform-launcher` makes `maven-failsafe-plugin` auto-detect the JUnit Platform provider and fail test discovery with `NoSuchMethodError` in `junit-platform-commons`, before any test actually runs — this happened once with an earlier draft of the `*RegressionIT` classes. Keep them (and everything else in this module) on `org.junit.Test`/`@BeforeClass`/`org.junit.Assert` (message-first argument order), matching the rest of the module.

### Regression-test `ChatModelConfig` values are copied from `config.yaml`, not loaded from it
`buildExtractorChatModel()`/`buildCheckerChatModel()` in `ClaimExtractorRegressionIT`/`FactCheckerRegressionIT` hardcode the same model name/`numCtx`/`numPredict`/temperature as `config.yaml` (loading it live would need a running Magnolia instance with JCR config, disproportionate for a Failsafe IT). If `config.yaml` changes, these methods need manual updates — nothing currently catches drift between them. A fast, Ollama-independent unit test that parses `config.yaml` and asserts it matches the hardcoded values would close this gap; not yet implemented.

### Reasoning-capable Ollama models can silently exhaust `numPredict` before producing output
Confirmed via `logRequests`/`logResponses` while evaluating `qwen3:14b`: a "thinking" model prepends an internal reasoning trace (Ollama response field `thinking`) that counts fully against `numPredict`. On a long enough input, that trace alone consumed the entire 1024-token budget dimensioned for the current (non-reasoning) production model, leaving `content` empty and causing `OutputParsingException: Failed to parse null (base64: null)` from `AiServices` — not a prompt or parsing bug. If a reasoning model is ever evaluated here again, either disable thinking explicitly (`OllamaChatModel.builder().think(false)`, supported by the LangChain4j version in use) or size `numPredict` generously enough to cover both the reasoning trace and the actual JSON response — raising `numPredict` alone without disabling thinking is not a reliable fix, since reasoning-trace length scales with input complexity and has no fixed upper bound.

### `qwen3:14b` is a diagnostic tool here, not a production candidate
Used once to disambiguate whether two regression-test failures were caused by a 7B-model capacity limit or by an actual prompt gap. It confirmed one (`river-duration-and-market-behavior-split`) was capacity-related — the larger model extracted the previously-dropped claim correctly — and revealed the other (`thematically-foreign-fact-in-marketing-copy`) was a too-strict test assertion, not a prompt bug (see below). At Q4 quantization it needs ~9.3GB, more than an 8GB-VRAM development GPU provides; the resulting CPU/RAM offload made even single requests take 100+ seconds in practice, well outside what's usable for an interactive editor-facing feature. Given this module's "lean", locally-runnable positioning, don't switch production to a model this size without also revisiting the target hardware assumptions.

### Cross-language extractor fixtures: assert on entities, not on a specific language's terminology
The `thematically-foreign-fact-in-marketing-copy` regression fixture embeds a German-language fact inside an English-language marketing text (`languageCode: "en"`). A correct extraction may legitimately translate the fact into the declared target language (e.g. "Bundeskanzlerin" → "Chancellor") — the system prompt's own "rewrite as a self-contained sentence" instruction makes this expected behavior, not a bug. The fixture's `mustContainSubstrings` therefore checks only the language-independent entity names (`"Anke Vossberg"`, `"Kordinia"`), not the office title, so a legitimate translation doesn't fail the assertion.

### Suggested regression cases from manual testing — now covered by `*RegressionIT`
These specific patterns, found through manual testing on real travel-domain content, are the ones the automated regression suite (fictional-content variants, see above) now exercises: cross-sentence coreference attributing a fact via "the capital"/"the city" to an entity named in an earlier sentence (including a case where a genuinely false claim must not be dropped); a superlative/acclaim sentence phrased differently from any few-shot example (tests generalization, not memorization); a compound sentence bundling a duration, a location, and a behavioral detail (split-rule regression); and a claim against a genuinely ambiguous named entity, exercising `isClearlyBestMatch`. If further prompt regressions turn up through manual testing, add them as new fixtures under `regression-testdata/` rather than as another list here.
